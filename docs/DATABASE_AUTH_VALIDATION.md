# MySQL·MariaDB와 JWT 인증 실제 검증

검증 시각: 2026-10-09 22:03 KST. 실제 로컬 서버에 HTTP 요청 **90회**를 보내 상태·저장값·쿠키·엑셀을 확인한 **157개 검증이 모두 통과**했습니다.

## 실행 환경

| 구분 | 실제 DB | 앱 주소 | 인증 저장소 |
| --- | --- | --- | --- |
| 기존 데이터 보존 | MySQL 8.4.11, `gyuhwan` | `127.0.0.1:8080`, `127.0.0.1:8081` | 공유 Redis 호환 Memurai, `127.0.0.1:6380` |
| 변경 테스트 | MariaDB 11.4.10, `gyuhwan_test` | `127.0.0.1:8082` | Redis 호환 Memurai |

두 DB의 문자셋은 `utf8mb4`, 정렬 규칙은 `utf8mb4_unicode_ci`였습니다. 세 앱의 liveness/readiness 요청이 모두 HTTP 200을 반환했습니다. 두 MySQL 앱은 같은 DB·JWT 서명 키·Redis를 사용했습니다.

## MySQL: 기존 데이터와 서버 간 인증

- 비로그인 관리자 설정·메인 내용·계정·기록·엑셀·로그인 정보 조회가 모두 401로 차단됐습니다. 공개 페이지와 공개 설정·내용은 정상 조회됐습니다.
- 실제 비밀번호 로그인과 CSRF 쿠키·헤더를 사용했습니다. JWT 쿠키는 `HttpOnly`, `SameSite=Strict`, `Path=/`, 만료 1,800초였으며 `JSESSIONID`는 발급되지 않았습니다. 로컬 HTTP 실행의 `COOKIE_SECURE=false` 조건에서 검사했습니다.
- 8080에서 받은 **동일한 JWT**로 8081의 관리자 정보를 조회했습니다. 두 서버가 같은 계정과 저장된 설정을 반환했습니다.
- 8081에서 로그아웃한 뒤, 복사해 둔 이전 JWT로 8080·8081을 각각 조회하면 **둘 다 401**을 반환했습니다. 다시 로그인하면 정상 조회됐습니다.
- 테스트 전후 가격·메인 내용의 전체 응답과 이력이 같았습니다. 각각 **버전 4, 이력 3건**을 유지했습니다. DB 직접 조회에서도 계정 1개·수정 기록 0건이 유지됐습니다.
- MySQL에서는 읽기와 별도 테스트 로그인·로그아웃만 수행했습니다.

## MariaDB: 저장과 변경 기록

- 한 가격 조건의 월정액 숫자 1개를 변경하고 다시 조회하여 저장값을 확인했습니다. CSRF 없는 저장은 403, 오래된 버전의 저장은 409였습니다.
- 메인 문구를 한글·이모지가 포함된 문자열로 변경했습니다. 공개 API 재조회와 DB의 JSON 값 직접 조회 모두 정확히 같은 문구를 반환했습니다.
- 가격과 메인 내용 기록에 작성자·대상·필드·변경 전후 값이 포함됐습니다. 가격 기록은 숫자 1개 변경을 정확히 구분했습니다.
- 대표 관리자가 일반 관리자를 추가했습니다. 일반 관리자는 다른 계정 목록을 조회할 수 없었고(403), 수정 기록은 조회할 수 있었습니다.
- 일반 관리자가 자기 아이디와 비밀번호를 변경하면 재로그인을 요구했습니다. **변경 전 JWT는 401**, 새 아이디·비밀번호 로그인은 성공했습니다.
- 계정 생성·변경 기록에 아이디의 변경 전후 값이 남았습니다. 비밀번호는 `설정됨`·`변경됨`으로 표시됐으며 실제 비밀번호는 기록 API에 포함되지 않았습니다.

최종 테스트 DB 상태는 가격 버전 3/이력 2건, 메인 내용 버전 2/이력 1건, 계정 2개, 수정 기록 5건입니다. 가격의 첫 번째 변경은 아래 CSRF 문제를 재현하던 중 저장된 테스트 변경입니다. 테스트 DB 자료는 검증 기록으로 유지했습니다.

## 엑셀 왕복

- 실제 내려받기 응답은 XLSX Content-Type과 UTF-8 한글 첨부 파일명을 제공했습니다. 파일 크기는 **105,943바이트**였습니다.
- ZIP/OOXML 내부를 읽어 `가격 정책` **864개 조건**, `모델 목록` **48개 모델**을 확인했습니다.
- 숫자 0과 빈칸의 셀 형식이 구분됐고 수식 태그는 없었습니다.
- 내려받은 파일의 업로드 미리보기는 변경 조건 0개·변경 필드 0개였습니다. 실제 재업로드 후에도 버전·이력·수정 기록이 모두 그대로였습니다.

## 실제 요청에서 발견한 CSRF 문제와 재검증

초기 실행에서는 JWT 인증 후 일반 GET이나 저장 응답이 CSRF 쿠키를 삭제하여 다음 저장이 403이 되는 문제가 재현됐습니다. JWT의 매 요청 인증에서 CSRF 인증 전략을 다시 실행하지 않도록 수정하고, 명시적인 로그인·로그아웃에서 토큰을 회전하도록 유지했습니다.

수정본에서는 인증된 GET과 정상 저장 뒤 CSRF 쿠키가 유지됐습니다. 보안 토큰을 새로 조회하지 않고 연속 저장·버전 충돌 검사·엑셀 업로드·계정 변경·로그아웃을 완료했습니다. CSRF 쿠키 삭제 응답은 명시적인 로그인·로그아웃에만 있었습니다.

## 자료와 범위

검증 도구·상세 결과·테스트 엑셀·테스트 입력은 로컬 `.runtime`에 보관했습니다. 결과 출력과 이 문서에는 비밀번호·JWT 원문·쿠키값을 넣지 않았습니다. DB 직접 조회는 저장된 JSON 유효성, 버전·이력 수, 한글·이모지와 변경 금액의 일치 여부를 추가 확인했습니다.

이는 로컬 MySQL·MariaDB와 두 앱 인스턴스의 실제 실행 결과입니다. 원격 Kubernetes/Swarm 클러스터, HTTPS 도메인, 운영 Redis 장애 복구나 공유 사진 스토리지의 실제 배포 검증은 포함하지 않습니다.
